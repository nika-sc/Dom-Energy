# История версий

## 4.14 — 21.11.2026 (полная сборка 1 630 192 Б; демо-образ в архиве 1 628 944 Б без ключа управления)

Один выпуск после 4.13 (11.11.2026): всё, что сделано с 11 по 21 ноября.
Прошивка **4.14**, сборка `6fe4b87d3a861ba37f1f`, образ **1 630 192 Б** —
82,9 % слота `min_spiffs` (1 966 080 Б). Страница `/` — ~86,3 КБ (86 331 Б отдаётся) Б
(в PROGMEM 86 655), `/app.css` 27 437 Б, `/app.js` 56 770 Б,
`/history.js` 63 122 Б, `/control.js` 5 868 Б. HTTP-эндпоинтов — **53**,
скинов — 6, экранов устройства — 10 (один, «СТОРОЖ», отключён).

### Источник, свежесть и честные нули
- **`GET /measure`** — по каждому показателю (напряжение, мощность, ток,
  температура) отдаётся `value`, `unit`, `source` (`local` / `cloud` / `none`),
  `ageSec`, `valid`, `local{…}`, `cloud{…}`, `ttlSec`. Отдельные TTL: 90 с для
  V/P/I, 300 с для T. Новый файл `firmware/cydv4/meas_sources.h`.
  Пример с живой платы: `voltage 235.8 В · source local · age 3 с`.
- **Возраст «не приходило ни разу» = `-1`**, а не `0`: в `/measure` (`ageSec`)
  и в `/storage` (`lastFailAgeSec`). Раньше 0 было неотличимо от «только что».
- **`/data` отдаёт `vSeen`, `pSeen`, `tSeen`, `stale`** — не полученные
  значения больше не показываются как реальные нули. В `/range` добавлены
  `vvalid` и `tvalid`: настоящий `0 °C` отличается от отсутствия измерения.
- **В интерфейсах видно источник и возраст**: веб и приложение пишут
  «локальное реле · 14 с», «облако · N с», «устарело · N мин», «нет свежих
  данных»; при `source=none` крупное число — «—». После двух сбоев опроса
  плашка «нет связи», при возрасте >20 с — «данные устарели» (плата может
  быть занята чтением истории).

### Честная математика истории
- **`null` больше не считается нулём.** В веб и Windows отсутствующее значение
  остаётся пробелом, `0` — валидной точкой; линия графика рвётся, а не падает
  в ноль. Бакет с неполными днями помечается «неполные данные».
- **Средняя мощность взвешивается по числу измерений** (`n`), мин/макс не
  выдаются за суточные экстремумы, недельный бакет обрезается выбранной датой.
- **24 ячейки истории всегда существуют**: клик, `←`/`→` и `Enter` выбирают
  любую ячейку, включая пустую — она показывает «нет измерений», а не
  перескакивает на первый столбик. Для экранных читалок — `aria-label`,
  `aria-live`, `aria-pressed`.

### SD-карта: запись, ротация, восстановление
- **`writeSd()` пишет строку в буфер и сверяет возврат записи.** В `/storage`
  добавлены `writeOk`, `writeFail`, `writeFailRun`, `lastWriteAgeSec`,
  `lastFailAgeSec`, `lastWriteErr`, `lastWriteMsg`, `freeBytes`, `archiveError`.
  Найденный по пути дефект: `f.size()` у FATFS не обновляется до `close()` —
  первая версия проверки считала успешную запись ошибкой.
- **`GET /repair?dedupe=1`** (нужен `X-Dom-Key`): оставляет первую строку на
  каждую секунду, исходник уходит в `/energy.bak`. На живой карте:
  2 356 722 → 1 956 791 Б, прочитано 52 227 строк, оставлено 43 338,
  удалено 8 358 точных дублей.
- **Восстановление после обрыва питания:** `initSD()` при отсутствии
  `/energy.csv` возвращает `/energy.bak` через `rename`, иначе `/energy.tmp`
  с предупреждением; пустой файл не создаётся. Тест `review-boot-recovery.ps1`
  — 11/11.
- **Месячные CSV и ревизии не удаляются по возрасту** — ротация сохраняет
  историю (`archive_transaction.h`). Новый `GET /storage` показывает ёмкость,
  свободное место и состояние записи.

### Архив и проверяемая передача
- На ПК — задача планировщика **`DomEnergy-DailyArchive`** (05:30 и после
  входа): контентно-адресные снимки SD, SHA-256 и gzip, без срока удаления;
  проверяемое локальное восстановление. Стенд на два года:
  2 105 280 строк / 109 474 560 исходных байт энергии.
- В приложении — новая вкладка **«Архив»**: статус задачи, последняя
  *проверенная* копия (собственная сверка SHA-256 всех 8 объектов), путь,
  свободное место, ошибка; кнопки «Снимок сейчас» (второй снимок не
  запускается) и «Тест восстановления» (`archive-sd.py --restore` во
  временную папку, SHA 8/8, удаляется только она).
- Полные приватные архивы устройства хранятся вне репозитория; в карточке
  архива — предупреждение, что PRIVATE-ZIP содержит flash и NVS и не
  подлежит публикации.

### Период: сравнение, пики, бюджет, экспорт
- **Сравнение периодов**: сегодня против вчера и выбранный диапазон против
  непосредственно предшествующего такой же длины. Разница в единицах и
  процентах — только при ненулевом знаменателе, иначе «—»; неполнота
  помечается, а не выдаётся за итог.
- **Пики нагрузки**: топ-5 наблюдённых часовых пиков с временем и кликом по
  часу, медиана часовой средней как оценка базовой нагрузки, число часов с
  данными. Малая выборка подписана «максимум среди полученных».
- **Бюджет и прогноз**: добровольный месячный лимит кВт·ч и/или ₽ (в вебе —
  `localStorage`, «хранится только в этом браузере»; в приложении — в
  `settings.json`), прогресс месяца, прогноз с явной пометкой «оценка»,
  методом и покрытием. Лимит 0 — без деления на ноль; нет лимита —
  приглашение, без выдуманных чисел.
- **Экспорт CSV** по выбранному диапазону: BOM UTF-8, CRLF, `;`, заголовок с
  единицами, пустые поля = пропуск (не ноль), имя файла с диапазоном.
  SD-файлы не читаются и не меняются; печать сохраняет диапазон и легенду.

### Климат: комната за период и T/H/P
- **`GET /climatehist?from=&to=`** — настоящий комнатный климат за период:
  по дням `n`, `tmin/tmax/tavg`, `hmin/hmax/havg`, `pavg`. Читает
  `/climate.csv` (дата, час, t, h, p), `0.0` = пропуск, дни без данных не
  выводятся. Чтение — хвост последних 64 КБ за ≤1,5 с; если до начала файла
  не дошли, отдаётся `partial:true` и `fileBytes`. Валидация `from/to` и
  ограничение 400 дней; ответ не ломается от битых параметров.
- В веб и приложении — «Комната за период» (средняя, взвешенная по `n`
  часам, мин/макс, влажность, давление, покрытие «N из M дней»), корреляции
  «t комнаты дня — кВт·ч дня», «t реле — кВт·ч», «t улицы — кВт·ч» при N≥5
  и с пометкой «связь не означает причину». Ровно **один запрос**
  `/climatehist` на смену периода (кэш, отмена устаревшего запроса), кнопка
  «Повторить» при ошибке, пометка неполных сегодняшних суток («сегодня:
  9 из 24 ч»). Живой пример: комната 25,7 °C (19,9–33,6, по 157 ч),
  влажность 63 % (47–88), давление 1020 гПа, покрытие 7 из 7.
- **Окно «КЛИМАТ» на плате**: кнопки **T / H / P** переключают величину
  графика, единицы (`%`, `мм`) — под графиком и в подписи выбранного часа;
  `/climate?data=1` отдаёт три ряда `hours`, `hum`, `pres`.
- **Спокойная шкала**: размах центрируется по среднему и имеет минимум —
  4 °C для температуры, 12 % для влажности, 8 мм для давления. Раньше
  0,1 °C растягивался на весь график.

### События, диагностика и обезличенный отчёт
- **Блок «События»**: хронология из `/vlog` и `/boots` (перезагрузки и их
  причина), старт текущей сессии, последняя ошибка облака — не более
  20 записей, «обновить». За время простоя события не выдумываются.
- **Блок «Диагностика»**: версия/сборка/uptime, источник и возраст V/P/I/T,
  LAN и WAN, SD, последний gapfill, последние строки `/clog`.
- **«Скопировать отчёт»** — обезличенный текст: без IP, MAC, SSID, токенов,
  device id и сырых измерений; только версия, состояния, коды ошибок, возраст
  данных и счётчики. Предпросмотр перед копированием, автоматических отправок нет.
  В Windows из путей маскируются `C:\Users\<имя>…` и прочие локальные пути.
- **`GET /stage`** — RTC-«хлебная крошка»: код последнего этапа `loop()`
  переживает панику и сброс, на старте пишется в `/boots.log` полем `st=`,
  а `/stage` отдаёт текущий и прошлый этап. Теперь место паники видно по
  HTTP, без USB. Плановая перезагрузка помечается `st=reboot`.
- **`GET /weather` и `GET /forecast`** — состояние, HTTP-код, ошибка, время,
  `heap`/`maxAlloc`; `?force=1` с ключом — принудительная попытка. Это
  позволило разобрать «погода не грузится» и «нет данных на завтра» без serial.

### Веб-страница
- **Один блок «Подробная статистика и таблица периода»** вместо двух

- **`/range` и `/history` стали асинхронными** — до готовности отдают
  202/pending, страница показывает «прочитано N КБ · считаю по дням…»,
  а не «Загрузка…».
- **Онлайн-мощность**: быстрый опрос `/data` раз в 1,5 с — ватты, ток и
  реле на лету, рядом «онлайн · N с».
- **Панель «Состояние и качество данных»**: LAN (плата отвечает, возраст
  `/data`, RSSI, реле, время, SD) и WAN (интернет, облако: токен/пауза/

- **Статика**: `/app.css`, `/app.js`, `/history.js`, `/control.js` — отдельные

- Свободное место на карте показывается честно: если `freeBytes` не сходится
  с `totalBytes − usedBytes`, считается по разности (страховка от старых

### Сеть, память и устойчивость
- **`pageCut` вылечен для обычной нагрузки**: для ответов >32 КБ пауза без
  прогресса поднята до 2500 мс, итог — обычно 20 из 20 загрузок (во время TLS-всплесков возможен редкий обрыв и у одиночного клиента) страницы (~86 КБ)
  целиком. Патологическая нагрузка (8 параллельных потоков × 10 загрузок)
  всё ещё даёт обрывы: сервер однопоточный, 86 КБ на соединение — это
  задокументированное ограничение, а не регрессия.
- **`bounded_web_server.h`**: 3 с + 50 мс/КБ на ответ, пауза без прогресса
  1500/600/150 мс по размеру. Стресс-тест: 120 подряд `/data`, 8 «молчащих»
  клиентов, 160 параллельных `/measure` — 0 отказов.
- **Меньше всплесков цикла (частично)**: источники всплесков цикла — TLS погоды/прогноза и
  `pwrfill/gapfill/облако`. Снижены таймауты погоды/прогноза, они не
  начинаются сразу после веб-запроса; перед TLS при нехватке памяти
  освобождается кэш суток. `loopMaxAll` снизился с 4654 до ~1,8–2,9 с;
  остаток — TLS-автоматика 1,5–3 с. Настоящий перенос TLS в отдельную
  задачу **не делался**: нужен стенд, риск для рабочей платы.
- **Облако**: `cloudTick()` обрабатывает ступени отказов один раз и не
  перезапускает рабочий Wi-Fi из-за ошибки облака; при свежем локальном
  напряжении облако не вызывается вовсе, но раз в 10 мин проверяется, и
  раз в 2 мин пробуется, если токена нет. В `/data` — `cHold`, `tok`.
- **`/climatehist` не блокирует сервер**: `yield()` и `esp_task_wdt_reset()`
  каждые 32 строки.

### Безопасность
- **`X-Dom-Key` для изменяющих маршрутов** (`/update`, `/reboot`, `/tap`,
  `/repair`, `/gapfill?run=1`, `/weather?force=1`, `/shot` и др.). Ключ
  хранится только локально: `%APPDATA%\DomMonitor\control.key` и
  `control-secret.h`; при отсутствии прошивочного ключа управление закрыто
  с HTTP 503. Открытие веба из приложения передаёт ключ через URL-фрагмент,
  браузер переносит его в `sessionStorage`. Чтение данных в LAN открыто.
- **CA для Tuya и OpenWeatherMap — в `trusted_roots.h`**; `setInsecure()`
  не возвращаем. Порт платы не публиковать в интернет: HTTP внутри LAN не
  шифрует трафик.
- **OTA только из приложения**: `POST /update`
  multipart-полем `firmware`, рядом с образом — `*.manifest.json` с SHA-256
  и идентификатором сборки; загрузчик проверяет ответ `OK`, сброс uptime,
  `/data.build` и доступность веба. Без выбранной сборки отказывает.
- В обезличенных отчётах и в Telegram-пинге нет токенов, device id и MAC.

### Telegram-пинг
- **`pc/DomTelegramPing.ps1`** — long-poll `getUpdates` рядом с приложением
  под супервизором: команда «пинг» (и «ping», «/status», «/now», «статус»,
  «состояние») возвращает полное состояние платы, «помощь»/«/help» — справку.
- **Только чтение**: бот делает GET `/data`, `/storage`, `/measure`,
  `/gapfill/status`, `/boots`; ни одной управляющей команды у него нет.
- **Доступ**: только личный чат, `chat.type=private`, `from.id=chat.id`;
  чужой чат игнорируется; битый `tgChatId` закрывает бота (fail-closed);
  авто-привязка — первые 10 минут после появления токена. Токен — только в
  `%APPDATA%\DomMonitor\tg-ping-config.json`, не в репозитории.
- Backoff при недоступном Telegram 5→10→20→40→60 с, offset без повторных
  ответов, лог с ротацией, мьютекс против второго экземпляра.
- Ограничение: **работает только при включённом ПК** и доступном Telegram.
